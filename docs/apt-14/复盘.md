# apt-14 敏感词"零宽插空"绕过（韩文填充符 / 星面代理对）复盘

- 现象来源：公寓楼年度检查——备注里夹"星号或空格"类字符即可从敏感词检测眼皮下溜走，违规备注照样发出、整改通知年年复发。

普通星号 `*`、半角/全角空格、常见标点、ZWSP 等零宽字符原本就能被正确剥离并命中（`DfaEngineTest` 早已覆盖）；真正漏掉的是两个**没有进"不可见字符"白名单**的字符族。

## 2. 缺陷一：韩文填充符——看着是空白，JDK 却当它是字母（主因，对中文词库有现实威胁）

### 2.1 复现

对 8 个种子词条（`代开发票/刷单返利/加微信/联系电话/赌博/私刻公章/有房出租/免押金`），用修复前引擎实测：

```
"赌ㅤ博"   → 归一化结果 "赌ᅠ博" → DFA 漏检（ㅤ = U+3164 HANGUL FILLER）
"赌ﾠ博"   → 同上（ﾠ = U+FFA0 半角韩文填充符，NFKC 折叠成 U+1160）
"赌ᅟ博"   → 漏检（U+115F HANGUL CHOSEONG FILLER）
"赌ᅠ博"   → 漏检（U+1160 HANGUL JUNGSEONG FILLER）
"代ㅤ开ㅤ发ㅤ票" → 漏检
"房间没问题，下午赌ㅤ博聚会别告诉物业" → 漏检
```

这些字符在浏览器/手机 UI 上**渲染为零宽空白，肉眼与空格（甚至比空格更隐蔽）无异**，管家复制粘贴、整改人刻意规避都极易带入，与工单"词里夹个空格就溜过去"的描述完全吻合。

### 2.2 根因

`TextNormalizer` 旧实现的最后一步是 `Character.isLetterOrDigit(c)` 判定保留：

```java
// JDK 8（Unicode 6.2 口径）实测：
Character.getType(0x3164) == OTHER_LETTER(5)
Character.isLetterOrDigit(0x3164) == true   // ← 零宽填充符被当成“字母”
```

- 普通空格/标点 → `isLetterOrDigit=false` → 被丢弃（所以空格插空一直能命中）；
- ZWSP/ZWNJ/ZWJ/BOM/软连字符等 → 在 `isInvisible()` 白名单里显式剥离；
- **但 4 个韩文填充符既不在白名单里、又被 JDK 归为 Lo 字母**，于是作为"有效字符"留在归一化文本里，挡在"赌"和"博"之间，DFA 转移失败，漏检。

全 Unicode 扫描（BMP 全部 + 0x10000–0x10FFFF 全部，见 2.4）确认：满足"视觉不可见 + `isLetterOrDigit=true`"的码点**只有这 4 个**，没有别的漏网字符。

### 2.3 修复

在 `TextNormalizer.isInvisible()` 中显式剥离 U+115F / U+1160 / U+3164 / U+FFA0（后一个在 NFKC 前拦，前三个在 NFKC 前后都拦，双保险）。修复后上述输入归一化结果均为 `赌博`/`代开发票`，正常命中，且命中区间覆盖填充符所在位置（打码一并遮蔽）。

### 2.4 排查方法（可复验）

- 全 BMP 扫描 `isLetterOrDigit=true` 且 Unicode 名含 FILLER/SPACE/INVISIBLE/BLANK/JOINER/SEPARATOR 的码点 → 仅 115F/1160/3164/FFA0；
- 全 Unicode 扫描"单码点 NFKC 折叠结果含这三个填充符"的码点 → 同样只有它们自身 4 个，不存在别的兼容字符间接折叠进来。

## 3. 缺陷二：星面数学字母——逐字符 NFKC 切断代理对，英文违禁词整体消失

### 3.1 复现

```
"𝐜𝐚𝐬𝐢𝐧𝐨"（U+1D41C… 数学粗体小写）→ 修复前归一化结果 ""（空串）→ 漏检
"𝓬𝓪𝓼𝓲𝓷𝓸"（数学花体）            → 漏检
"earn 𝐜𝐚𝐬𝐢𝐧𝐨 now"              → 漏检
对照：Normalizer.normalize("𝐜𝐚𝐬𝐢𝐧𝐨", NFKC) = "casino"（整串折叠本可命中）
```

### 3.2 根因

归一化注释自称"逐字符 NFKC"，实现是 `for (int i = 0; i < raw.length(); i++) char ch = raw.charAt(i)`。
星面字符在 Java 中是**代理对（2 个 char）**，把高代理位 `\uD835`、低代理位 `\uDC1C` 分别单独送 NFKC 都保持原样，而孤立代理位既不是字母数字也不在不可见白名单 → 被静默丢弃。整条英文词因此消失，比"夹一个字符"更彻底。

### 3.3 修复

- 遍历改为**按 Unicode 码点**（`codePointAt` + `Character.charCount`），折叠后产出的多个字符共享同一个原文起始下标，位置映射语义不变；
- `DfaMatcher` 计算命中区间结尾时，末字宽度由固定 `+1` 改为 `Character.charCount(codePointAt(...))`：BMP 仍是 `+1`，星面字符为 `+2`，打码区间覆盖完整代理对，不会留下孤立低代理位产生脏字符；
- 顺手补齐补充平面变体选择符 VS17..VS256（U+E0100..U+E01EF）的剥离（旧白名单只到 BMP 的 VS16）。

全 Unicode 扫描确认：补充平面不存在"不可见但算字母"的其他码点；数学字母区单码点 NFKC 折叠均在码点内完成（1 个代理对 → 1 个 BMP 字符），按码点归一化位置映射可靠。

## 4. 补丁清单（独立评审用）

## 6. 同类隐患排查结论

### 6.1 归一化层（本次全部修复）

- 韩文填充符 4 码点：修复；
- 星面代理对被切断（数学粗体/花体/无衬线等整套字母数字都受影响）：修复；
- VS17..VS256 补充变体选择符：修复；
- 已逐一验证**仍不拦截**但属**词库/语义层固有边界**、不应靠归一化硬凑的手法：
  - **拆字/错字**：`者贝才`（赌）、`赌愽`（愽 bó，生僻形近字）——需要拆字词典或收录变体词条；
  - **繁体**：`賭博`——建议词库补录繁简双形（当前 8 个种子词均只有简体）；
  - **拼音/谐音、emoji 替字**：`du博`、`赌🀄博` 类——属运营词库策略，建议在 `t_sensitive_word` 增补变体而不是扩归一化规则（扩规则会推高误伤）。

### 6.2 字段覆盖层（漏挂 `SensitiveGuard.checkField` 的写入点，建议按单跟进，**未纳入本补丁**）

对全部 196 个生产类做了字段级走查（请求 DTO 自由文本 → mapper 落库的每一处）。除已挂检查的 5 个服务（Checkout/Lease/PropertyLedger/Handover/AsyncTask 共 9 处调用）外，确认以下漏挂：

| # | 位置 | 字段 | 落库/出口 | 风险 |
|---|---|---|---|---|
| 1 | `tree/service/PropertyTreeService.java:71` | `nodeName` | `t_property_node.node_name` | 节点名可直接写违规广告/备注，完全无拦截 |
| 2 | 同文件 :73（建根节点） | `community` | `t_property_node.community` | 同上 |
| 3 | `report/service/SignReportService.java:330` | `buildingName` | `t_sign_report_version`，并派生 `fileName`、渲染进归档 docx 落盘 | 违规文本进入**正式签约报告文件**，外发风险最高 |
| 4 | 同文件 :331（请求显式传入分支） | `community` | 版本表 + docx 页眉 | 同上 |
| 5 | `quota/QuotaService.java:100` | `community`（预占申请） | `t_quota_hold`，派生 `t_quota_journal` | 内部台账污染，外发面小 |
| 6 | 同文件 :258（开户） | `community`（调整申请） | `t_quota_balance` + journal | 同上 |
| 7 | `service/LeaseService.java:64` | `emergencyContact.relation`（嵌套 JSON 整体落库，`name` 同流） | `t_lease.emergency_contact` | 关系字段无豁免依据；姓名是否扫描需业务定口径 |

需业务确认口径的两项：
- `tenantName`（`LeaseService:61`、`AsyncTaskService:125`、`SignArchiveBusinessOps:72`）：类注释明确"姓名/手机/证件属结构化信息不扫，避免误伤"，且出口侧已有 `@Sensitive` 脱敏——**有意豁免**，建议保留但补一行注释把豁免清单写明；
- `CheckoutRequest.inspectionResult`：实体只取 PASS/DAMAGE 码值，风险低，可不扫。

已排除的疑似点：
- **电子签回调** `ESignSignCallbackRequest.remark`：`ESignCallbackService` 根本不读取该字段（死字段），无落库；日后启用前必须先挂检查；
- `SensitiveWordService` 落库的 `wordText/remark`：管理面收录的就是敏感词本身，不能过自己这关，属合理豁免；
- RBAC 账号/角色、拼音验收（常量）、任务 failReason（异常消息非请求文本）均无请求自由文本落库。

### 6.3 建议

1. 本补丁先上（堵住已被年检点名的绕过路径，改动小可独立评审/回滚）；
2. 6.2 的 1–4 项（树节点、签约报告）建议本期内补挂 `checkField`——签约报告是外发文件，优先级最高；5–7 项排下一期；
3. 词库补录 8 个种子词的繁体/常见错写变体（`賭博/賭愽?` 等），并把"新增变体词条"写进敏感词运营 SOP；
4. 给 `checkField` 增加 AOP/注解化覆盖（字段打注解开扫描），替代当前"手工逐字段调用"模式，从机制上消灭"新写字段漏挂"这一类问题。
