# apt-15 运维日志"按合同号聚合混进别人单号"复盘与验证步骤

- 排查/修复日期：2026-09-26
- 环境：Amazon Corretto 1.8.0_504、Apache Maven 3.9.9、Spring Boot 2.7.18、H2 2.1.214
- 涉及模块：`com.evops.common.trace`、`com.evops.apartment.task.engine`
- 现象来源：管家工单——按合同号聚合日志时，一个请求的日志里混进了别人的单号，排查方向被带偏；月初已报过一次。

## 1. 结论速览

| 项 | 结论 |
|---|---|
| 现象是否属实 | **属实（结构性缺陷，可证明）**。当前配置下线上日志/运维库未查到正在发生的串号；但边界不消毒的缺陷客观存在，线程一旦带上外来上下文，整个请求的日志（含入库的 http-access 行）就会挂到别人单号下——修复前有 pinpoint 测试稳定复现 |
| 根因层级 | 入口过滤器边界（`TraceFilter`），不是某个业务服务忘了清理 |
| 主补丁 | 3 个生产文件：`TraceFilter.java`、`TaskExecutor.java`、`TraceContext.java`（仅注释对齐）；另加 2 个回归测试类 |
| 回归结果 | 新增 3 个用例全绿；全量 `mvn test` **116/116 通过**，既有口径零回退 |
| 演示验证 | `docs/apt-15/verify-trace-boundary.sh` 对运行中服务一键校验 12 项，全绿 |

## 2. 核实过程（先核实，后动手）

按"是否属实"先做了四层核查，**未**直接改代码：

1. **存量日志核查**（`logs/evops-base*.log*`，09-23 至今约 10 万行）：
   - 一个 traceId 关联多个合同号：仅 1 例，是 `/api/apartment/leases/acceptance/samples`
     批量播种端点（一个请求建 5 份合同），属设计内行为；
   - http-access 访问行带合同号：0 例；
   - MDC 合同号与消息体合同号不一致：0 例。
2. **运维库核查**（`t_ops_log_entry` 全量 65 行）：无串号行。
3. **静态审计**：6 处合同号绑定（LeaseService/CheckoutService/QuotaService/
   PropertyTreeService/AsyncTaskService/TaskExecutor）均有对称还原；过滤器、
   装饰器、执行器的清理路径逐一过一遍，主流程闭环。
4. **复现测试**：同线程连续请求（成功/异常分支/纯查询）+ 工作线程跨任务复用
   （`TraceContextIsolationReproTest`），当前代码下**不**复现串号。

**结论**：当前配置（`evops.trace.enabled=true`）下主流程不串号；但"不串号"这件事
**完全靠每个调用方自觉还原**——边界（入口过滤器）只在请求**出口**清理、且清理动作
被功能开关门控，入口从不消毒。这正是管家说的"不能靠自觉"：任何一条没覆盖到的路径
（非 `/api/*` 端点、应急关闭 trace 的窗口、未来新加的绑定代码）把上下文留在线程上，
下一个请求就会全程带着别人的单号打日志、进运维库。

## 3. 根因

### 3.1 主根因：入口不消毒，出口清理还被开关门控（`TraceFilter`）

修复前 `TraceFilter.doFilterInternal`：

```java
if (properties.isEnabled()) {
    traceId = resolveInbound(...);
    TraceContext.setTraceId(traceId);   // 只覆盖 traceId；contractNo/username 残留原样带入
}
...
} finally {
    if (properties.isEnabled()) {        // 清理被开关门控：应急关闭 trace 时完全不清理
        ...
        TraceContext.clear();
    }
}
```

- 线程带着外来上下文进入请求时，入口只覆盖 traceId，**残留的合同号原样穿过整个请求**；
  请求结束时的 http-access 行（固定入库）就带着别人单号落进 `t_ops_log_entry`，
  管家按该单号聚合即看到这次无关请求的日志——与工单现象一致。
- 业务服务绑定合同号**不随** `evops.trace.enabled` 开关，但边界清理**随**开关：
  应急关闭窗口内，边界对残留完全放任。

### 3.2 次根因：响应头与日志两个数据源

修复前响应头取自过滤器局部变量、日志取自 MDC，两份数据靠"流程上不会分叉"维持一致；
注释声称"追踪关闭也回带网关注入值"，代码实际不回带（注释与实现漂移）。

### 3.3 工作线程侧同理

`TaskExecutor.claimAndRun` 只在 finally 清理，绑定前不消毒——池化线程若有残留，
任务的日志同样被污染。

## 4. 修复内容（把规矩定进系统）

| 文件 | 改动 |
|---|---|
| `TraceFilter.java` | ① **入口先 `TraceContext.clear()` 再绑定**：请求从干净上下文开始，链路号线程内唯一由边界保证；② **响应头从 MDC 回读写出**（`TraceContext.getTraceId()`），与日志/运维库同一份事实，响应头与日志同源；③ **出口清理不再被 `enabled` 门控**（访问日志仍随开关）；④ 追踪关闭时合法入站值按注释口径回带（补齐注释与实现漂移） |
| `TaskExecutor.java` | `claimAndRun` 绑定任务上下文**前先 `TraceContext.clear()`**，工作线程侧同一铁律 |
| `TraceContext.java` | 类注释与边界铁律对齐（无行为变更） |

回归测试（新增 2 类 3 例）：

- `TraceBoundaryInvariantTest`：线程被人为塞入外来链路号+合同号后发起请求，
  断言本请求日志（含入库 http-access 行）不挂外来单号、响应头/体同源、
  外来单号名下聚合不到本请求日志。**修复前该测试失败**（http-access 行带着
  `HT-FOREIGN-LEAK-0001` 入库），修复后通过——这就是"串号"的 pinpoint 证据链。
- `TraceContextIsolationReproTest`：同线程连续请求（成功/唯一冲突异常/纯查询/他合同）
  与工作线程跨任务复用，断言任何链路号下不出现外来合同号。

## 5. 回归验证

- 修复前 pinpoint：`TraceBoundaryInvariantTest` **失败**，失败行即工单现象——
  `本请求日志混入外来合同号: contractNo=HT-FOREIGN-LEAK-0001 logger=com.evops.access
  msg=http-access GET /api/apartment/leases -> 200`；
- 修复后：新增 3 例全绿；全量 `mvn test` **116/116 通过**；
- 真机演示（18080 端口独立实例）：`docs/apt-15/verify-trace-boundary.sh` **12/12 通过**，
  其中合同 C 的签约归档任务从提交到后台 20 步共 12 行日志全部同一链路号。

## 6. 管家可演示验证步骤

### 6.1 一键脚本（推荐）

```bash
# 终端 1：启动应用
mvn spring-boot:run            # 或 java -jar target/evops-base-0.1.0-SNAPSHOT.jar

# 终端 2：跑验证脚本（12 项检查）
bash docs/apt-15/verify-trace-boundary.sh
```

脚本覆盖：健康检查 → 登录 → 响应头/体同源 → 两合同建档互不串号 →
签约归档任务前后台同一链路号 → 非法入站链路号被拒 → 输出通过项数。
幂等，可重复执行（每次时间戳生成新合同号）。

### 6.2 手工演示（运维日志检索台）

1. 浏览器打开 `http://localhost:8080/api/apartment/ops-log/console`，贴管家令牌；
2. 用脚本第 4 步打印的合同号（如 `HT-D15-A-xxx`）检索：所有行 `contractNo` 均为该合同、
   `traceId` 均为该次请求响应头里的值——**响应头与日志同源**；
3. 再换合同 B 检索：结果里**没有**合同 A 的任何行——**按合同号聚合不混单**；
4. 用合同 C（签约归档任务）检索：提交请求与后台 20 步的日志在**同一个链路号**下聚齐。

### 6.3 自动化守卫（防回退）

```bash
mvn test -Dtest=TraceBoundaryInvariantTest,TraceContextIsolationReproTest
```

任何人把边界清理改回"靠自觉"、或让响应头与日志分叉，这两个测试类立即失败。

## 7. 影响面与回滚

- 行为变化仅在边界：入口多一次 MDC 清空（此前依赖出口清理与各服务自觉还原）、
  响应头改从 MDC 回读（值不变）、出口清理不再随 `enabled` 开关、
  追踪关闭时合法入站值回带（补齐既有注释口径）。无 schema/接口/配置变更。
- 回滚：还原 `TraceFilter.java`、`TaskExecutor.java` 两个文件即可；
  删除两个新增测试类与 `docs/apt-15/` 不影响运行行为。
