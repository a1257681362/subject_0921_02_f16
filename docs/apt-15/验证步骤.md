# apt-15 链路号线程内唯一 + 响应头与日志同源 验证步骤

- 模块：`com.evops.common.trace`、`com.evops.apartment.task.engine.TaskExecutor`
- 日期：2026-09-26
- 背景：月初有人反馈"按合同号聚合日志时，一个请求的日志里混进别人的单号，排查方向被带偏"。

## 1. 根因（这次查到根上，不再靠自觉）

合同号/TraceId/账号都存在 SLF4J MDC（线程级），而容器线程与任务工作线程都是**池化复用**的。
旧实现把"绑了要记得恢复/清空"分摊给每个业务方法自己写 finally，系统没有强制边界，具体三处：

1. **空值不覆盖（直接串号源）**：`bindContract(null)`/`setUsername(null)` 是静默 no-op。
   后台任务 `biz_ref`/`operator` 为空（预留任务类型、历史脏数据）时，池化工作线程复跑该任务，
   整单 20 步日志全部挂在**上一单的合同号/操作人**名下；任务记录查不到时甚至完全不绑就执行。
2. **入口不清场**：`TraceFilter` 只写 traceId，从不清合同号/账号；请求开始不做无条件清空，
   一旦上游某个绑定点漏写 finally（新增入口最容易犯），下一请求线程上首段日志就带上别人的单号。
3. **响应头与日志不同源**：响应头用过滤器局部变量写，日志/响应体读 MDC；
   `evops.trace.enabled=false` 时网关注入的头照样回带，日志却是 `traceId=N/A`——
   管家凭响应头去运维日志菜单查，一行都查不到。

## 2. 修复（规矩定进系统）

- `TraceContext` 三个 setter 全部改为**权威写：空值即摘除**，新增 `contractScope(...)`
  （try-with-resources，关闭必还原），业务入口统一改用作用域，删除 6 处手写"暂存—finally 恢复"。
- `TraceFilter`：请求开始**无条件 `MDC.clear()`**（双保险：结束也清）；
  响应头 `X-Trace-Id` **直接取 MDC 当前值**，与文件日志、采集库、响应体严格同源；
  追踪关闭时不生成、不回带头。
- `TaskExecutor.claimAndRun`：认领任务时先**无条件清空**工作线程 MDC，再按任务表重绑；
  任务记录查不到时以空上下文执行并立即退出，绝不带旧上下文跑。

## 3. 自动化回归

```bash
mvn -Dtest=TraceContextBoundaryTest,WorkerMdcIsolationFlowTest test
```

- `TraceContextBoundaryTest`：空值绑定摘除残留；作用域异常退出也还原；过滤器清掉线程上
  "上一请求"的 traceId/合同号/账号；响应头 == 日志 MDC 值；关闭追踪不回带头。
- `WorkerMdcIsolationFlowTest`：池化工作线程带残留上下文认领一个无合同号任务，
  步骤日志必须只带本任务 traceId 且合同号为空；同一线程连跑两单，各单日志只带自己的号。

## 4. 可演示手工验证步骤（管家视角）

### 4.1 响应头与日志同源（30 秒）

```bash
# 1) 自报 TraceId：响应头、响应体必须同值
curl -s -D - -o /tmp/body.json \
  -H "X-Trace-Id: demo-trace-0001" \
  "http://localhost:8080/api/apartment/leases" | grep -i X-Trace-Id
cat /tmp/body.json            # $.traceId 必须也是 demo-trace-0001

# 2) 文件日志同一行同一个号
grep "demo-trace-0001" logs/evops-base.log | tail -5

# 3) 运维日志菜单按该 TraceId 检索，命中行的 traceId 与响应头一字不差
#    （页面：/api/apartment/ops-log/console，粘管家令牌）
```

### 4.2 并发两单互不串号（核心演示）

1. 管家账号连续/并发发起两笔不同合同的业务（建档 或 签约归档）：
   `HT-DEMO-A`、`HT-DEMO-B`，分别带不同的 `X-Trace-Id`（`trace-A-0001`/`trace-B-0001`）。
2. 文件日志按合同号过滤：

   ```bash
   grep "contractNo=HT-DEMO-A" logs/evops-base.log | grep -o "traceId=[^ ]*" | sort -u
   # 期望：只有 traceId=trace-A-0001（后台任务同号），绝不出现 trace-B-0001
   grep "contractNo=HT-DEMO-B" logs/evops-base.log | grep -o "traceId=[^ ]*" | sort -u
   # 期望：只有 traceId=trace-B-0001
   ```

3. 反向按 TraceId 聚合，合同号集合大小必须为 1：

   ```bash
   grep "traceId=trace-A-0001" logs/evops-base.log | grep -o "contractNo=[^ ]*" | sort -u
   # 期望：contractNo=HT-DEMO-A（无业务段为 N/A 属正常，绝不出现 HT-DEMO-B）
   ```

4. 在运维日志菜单按合同号 `HT-DEMO-A` 检索：全部行 traceId 一致；
   等签约后台任务跑完，`执行成功 100%` 行也是同一个 traceId（工作线程续传）。

### 4.3 池化线程复用不带上一单（工作线程）

- 用 mock 演示连续发起 ≥3 个签约归档任务（`/api/esign-demo/console` 可看节奏），
  等全部 SUCCESS 后：

  ```bash
  # async-task-1/2 上每个 traceId 只能对应一个合同号
  python3 - <<'PY'
  import re, collections
  tc = collections.defaultdict(set)
  for line in open('logs/evops-base.log', encoding='utf-8', errors='replace'):
      m = re.search(r'\[(?:evops-base),(async-task-\d+)\] traceId=(\S+) contractNo=(\S+)', line)
      if m and m.group(3) != 'N/A':
          tc[m.group(2)].add(m.group(3))
  bad = {t: c for t, c in tc.items() if len(c) > 1}
  print('串号 trace 数:', len(bad), bad)   # 期望：0 {}
  PY
  ```
