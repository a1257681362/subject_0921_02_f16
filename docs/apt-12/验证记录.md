## 1. 缺陷确认（属实）

安全抽查称：导出的租约文件里证件号打码了，同表紧急联系人电话却是明文，规则配了全表。
按线上结构补齐 `t_lease.emergency_contact`（JSON 嵌套对象：姓名/电话/关系）后，
用**修复前代码**在真实服务进程（8080 端口，文件库 `data/evops`）复现：

- 建档 `HT-REPRO-0001`（张三 / 13800000000 / 110101199001011234，
  紧急联系人 王五 / 13912345678 / 配偶）；
- 导出 CSV（`evidence/export-before-fix.csv`）：

```csv
HT-REPRO-0001,PROP-A-101,张*,138****0000,110101********1234,...,"EmergencyContact(name=王五, phone=13912345678, relation=配偶)"
```

- 扁平字段（姓名/手机号/证件号）全部按规则打码 ✅；
- **紧急联系人（嵌套对象）整棵明文带出，电话 13912345678 未打码** ❌ —— 与抽查一致，**确认属实**。
- 同一时刻接口 JSON（`evidence/api-before-fix.json`）嵌套成员是打码的
  （`"name":"王*","phone":"139****5678"`）——证实缺陷在导出口的反射读取，不在规则配置。
- 日志出口同患（`evidence/log-before-fix.txt`）：既有日志里
  `签署链接已送达租客 张三` 为明文（文件日志与 `t_ops_log_entry` 采集同染）。

**根因**：`SensitiveFields.readAsString` 只处理实体上的扁平 String 字段，
未打 `@Sensitive` 的字段一律 `value.toString()` 原样返回，嵌套对象内部的
`@Sensitive` 成员根本不会被遍历；日志语句另有几处直接拼明文姓名。

## 2. 修复内容

1. `SensitiveFields` 重构为**嵌套对象递归脱敏**：
   - 字段值是嵌套 bean / Map / 集合 / 数组时深度遍历，凡 `@Sensitive` 字段一律按
     `SensitiveRuleRegistry` 同规则脱敏，渲染为 JSON（字段声明序）；
   - 新增 `maskValue(type, value)`（单值）与 `toMaskedJson(obj)`（整对象）供日志出口；
     口径与接口对齐（`@JsonIgnore` 不输出），循环引用截断为 null 防死循环；
   - 规则来源不变（`application.yml` 默认底 + `config/sensitive-rules.yml` 热加载），
     嵌套层级与扁平字段同一份规则。
2. 日志出口同规则（5 处）：`SignArchiveStepHandler` 步骤 10、
   `MockESignPlatformClient.startTenantSign`、`PinyinIndexer` 三处截断告警，
   姓名改经 `SensitiveFields.maskValue(NAME, …)`。
3. 缺陷载体补齐：`t_lease.emergency_contact`（JSON 列，库内明文，与
   “脱敏只在出口”口径一致；存储 TypeHandler 关闭 Jackson 注解防误脱敏落库）；
   租约导出新增「紧急联系人」末列。
