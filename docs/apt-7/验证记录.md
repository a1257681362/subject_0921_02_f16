### 关键不变量（被上述用例反复验证）

1. **不超扣**：申请是 `UPDATE ... WHERE total-occupied-reserved >= 1` 单条条件更新，行锁串行化，不足 0 行；
2. **账实相符**：`balance.reserved_amount` 恒等于该小区 `status='HELD'` 预占单 `reserve_amount` 之和（用例 1/3/5/7/9/13 均断言 `sumHeldReserved`）；
3. **只释放一次**：确认/取消/超时全部 `WHERE status='HELD'` CAS，竞争下只有一方动账写流水；
4. **流水可回放**：每条流水带变化后三余额，逐步累加必等于快照与现值。

## 3. 实现过程中发现并修复的问题（留档）

1. **路径单号被请求体校验拦截**：确认/取消接口的 `holdNo` 来自路径变量，DTO 上却带了
   `@NotBlank`，请求体不传该字段时 `MethodArgumentNotValidException` 在进方法前就返回
   200/`success=false`，导致 SELF 越权操作本应 403 却被校验抢先返回。
   → 去掉 body 内 `holdNo` 必填、服务层补空值防御；范围校验先于业务执行，越权稳定 403。
2. **同单唯一索引初版会误拒「二次申请」**：最初用 `UNIQUE(biz_ref, status)`，
   同一合同释放两次后会出现两条 `(biz_ref,'RELEASED')` 冲突。
   → 改为 H2 生成列 `active_biz_ref`（仅 HELD/CONFIRMED 取 biz_ref，释放为 NULL）
   + 唯一索引（NULL 不参与唯一），语义精确为「同时只有一笔活跃单」。
3. **取消/超时竞争的提示不分原因**：取消分支对已释放单一律「无需重复取消」，
   管家遇到恰被超时释放时看不出原因。
   → 按 `release_reason` 区分，明确回「已被超时自动释放，取消未生效」（用例 10 断言）。
4. **确认与超时竞争会冒系统错误**：确认先通过过期检查、随后被超时扫描释放时，
   CAS 落空原抛 `IllegalStateException`（被兜底成「系统处理失败」）。
   → 改为重读单据状态返回业务失败「已超时自动释放，确认未生效」（用例 11 断言），
   不动账、不写 CONFIRM 流水。

## 4. 设计取舍说明（管家关心的口径）

- **额度按小区维度**：与台账 `community`、apt-3 SCOPE 授权小区口径一致；
  预占固定占 1（一次租约建档对应一个出租名额），调用方不能指定数量，防多占。
- **预占不与租约建档强绑事务**：本期先交付独立预占能力（年检先过），后续租约建档/签约任务
  可在同一事务内调用申请+确认串起来；模型接口不变。已实扣额度的最终释放仍走既有退租流程。
- **超时只自动释放、不自动确认**：到期即视为放弃，避免把 20 分钟前的余量判断固化成实扣。
